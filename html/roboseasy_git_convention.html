브랜치 전략

STRUCT
main / develop / feature/{이름} — 3단 구조
브랜치용도규칙
main완료된 프로젝트의 최종 코드프로젝트 완료 시 develop에서 머지
develop진행중인 프로젝트의 최신 코드feature 브랜치의 머지 대상
feature/{이름}각 기능별 개발 브랜치develop에서 분기, 완성 후 develop으로 머지
✓ GOOD
# 예: so-arm 레포에서 IK 연구와 VLA 연구를 각각 진행하는 경우
main
develop
feature/ik
feature/vla

# feature 브랜치 생성 — develop에서 분기
git switch develop
git switch -c feature/ik

# 작업 완료 후 develop으로 머지
git switch develop
git merge feature/ik
git push origin develop
⚠️ 주의: 각 개발자는 자신의 feature 브랜치에서만 작업한다. main과 develop에서 직접 커밋하지 않는다.

커밋 메시지 형식 ⭐

COMMIT
Tag: 한줄 설명 — 태그는 대문자로 시작, 콜론(:) 뒤 공백 1개

제목은 한 줄로 무엇을 왜 했는지 요약한다 (50자 이내 권장). 한국어 작성을 허용하며 끝에 마침표를 붙이지 않는다. 커밋 메시지만 보고도 "무엇을 했는지" 파악되어야 한다.

✓ GOOD
Add: IK solver 초기 구현
Fix: VLA 모델 입력 차원 오류 수정
Improve: 관절 보간 알고리즘 성능 개선
Delete: 사용하지 않는 테스트 파일 제거
Merge: feature/ik를 develop에 머지
✗ BAD
add: ik solver   # 소문자 태그 X
Add : IK solver  # 콜론 앞 공백 X
Add:IK solver    # 콜론 뒤 공백 없음 X
수정함            # 태그 없음 X
Fix: 버그 수정    # 무엇을 고쳤는지 알 수 없음 X
Add: IK 추가하고 URDF 오타도 수정
                 # 두 가지 목적 X → 커밋 분리

커밋 단위

COMMIT
1 커밋 = 1 목적 (atomic commit)

하나의 커밋에는 하나의 논리적 변경만 담는다. 태그를 하나로 정할 수 없다면 커밋을 분리하라는 신호다.

✓ GOOD — 목적별로 분리
Add: FSR 센서 드라이버 노드 추가
Fix: IMU 콜백 타임스탬프 오류 수정
Docs: README에 실행 방법 추가
✗ BAD — 한 커밋에 여러 목적
Add: FSR 드라이버 추가, IMU 버그 수정,
     README 정리
💡 팁: 커밋을 자주, 작게 남기면 문제 발생 시 git revert / git bisect로 원인 커밋을 쉽게 찾을 수 있다.

머지 규칙

FLOW
feature → develop → main 방향으로만 머지

feature 완성 → develop으로 머지 (Merge: 태그). 프로젝트 완료 → develop을 main으로 머지. 충돌(conflict)은 feature 브랜치 쪽에서 해결한 후 머지한다. 협업 레포에서는 GitHub Pull Request를 통한 머지를 권장한다 (리뷰 1인 이상).

✓ GOOD
# 머지 전 develop 최신화 후 feature에서 충돌 해결
git switch feature/ik
git pull origin develop     # 충돌 발생 시 여기서 해결
git switch develop
git merge feature/ik

버전 태그 (Release)

RELEASE
v 접두사 + Semantic Versioning (vMAJOR.MINOR.PATCH)
자리올리는 시점예시
MAJOR호환성이 깨지는 변경v1.x.x → v2.0.0
MINOR기능 추가 (호환 유지)v1.0.x → v1.1.0
PATCH버그 수정v1.0.0 → v1.0.1
✓ GOOD
git tag -a v1.2.0 -m "Release: v1.2.0"
git push origin v1.2.0

금지 사항 🚫

SAFETY
공유 브랜치와 레포를 보호하는 최소 안전 규칙
금지 항목이유
main / develop에 직접 push리뷰 없는 코드가 공유 브랜치를 오염
공유 브랜치에 git push --force팀원의 커밋 이력이 사라짐
비밀정보 커밋 (토큰, 키, 비밀번호)한 번 push되면 이력에 영구 잔존
빌드 산출물 커밋 (build/, install/, log/)레포 용량 증가, 충돌 유발
대용량 바이너리 커밋 (rosbag, 학습 weight)100MB 초과 시 push 거부, clone 속도 저하
개인 설정 파일 커밋 (.vscode/, IDE 설정)팀원 환경을 덮어씀
⚠️ 주의: 비밀정보를 실수로 커밋했다면 즉시 팀에 공유하고 해당 키를 폐기 · 재발급한다. 커밋 삭제만으로는 안전하지 않다.
